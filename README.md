# TradeLab

TradeLab — пет-проект для GitHub-портфолио: веб-сервис для тестирования
криптовалютных торговых стратегий на исторических данных (backtesting).
Основа проекта — собственный движок на Go. Финансовые и статистические
вычисления выполняются на backend.

TradeLab — инструмент исторического моделирования, а не финансовый совет.
Результаты на истории не гарантируют будущую доходность.

## Технологии и статус

Этапы 1–6 завершены. По результатам ручного деплоя backend работает на Render Free:
https://tradelab-api-thrx.onrender.com. Docker-сборка и локальный запуск проверены
29.10.2026 после переноса disk image на D:.
Полная [инструкция Docker / Render Free](docs/deployment.md) включает проверку
диска D:, результаты контейнерных проверок, ручной deploy и команды тестирования
Binance именно с хостинга.

Windows: ресурсоёмкие проверки выполняются из `D:\go_projects\TradeLab`,
с `GOCACHE=D:\GoCache`, `GOMODCACHE=D:\GoModCache`, `GOTMPDIR=D:\GoTemp`.
Перед `docker build` обязательно проверьте Disk image location в Docker Desktop:
переменные Go и расположение checkout сами по себе не переносят Docker storage.

После ручного переноса, из checkout на D::

```powershell
docker build --platform linux/amd64 -t tradelab-api .
docker run --rm -p 8080:8080 -e PORT=8080 tradelab-api
```

Ручной Render: New → Web Service → репозиторий TradeLab → Docker → Free →
Health Check Path `/healthz`, Auto-Deploy Off. `PORT` предоставляет Render;
`CORS_ALLOWED_ORIGINS` — точные frontend origins или пустое значение.
Нажатие Create Web Service — отдельное действие деплоя, здесь не выполненное.
Free засыпает после 15 минут простоя, холодный старт обычно занимает около
минуты; [ограничения и учёт потребления](https://render.com/docs/free) необходимо
проверить до создания ресурса. Постоянный фоновый процесс проекту не требуется.

Демонстрация без Binance и без нового публичного endpoint:

```powershell
go run ./cmd/marketcheck -fixture -backtest
```

Результат явно помечен `source: fixture`; это синтетический Buy & Hold сценарий.

Реализованы этапы 1–5: HTTP-сервер на стандартном `net/http`, конфигурация
порта, JSON-логи через `log/slog`, graceful shutdown и независимое расчётное
ядро бэктестинга с unit-тестами. Ядро принимает готовые сигналы и выполняет
симуляцию Spot-торговли по историческим OHLCV-свечам. Добавлены стратегии
SMA Crossover и Buy & Hold, показатели эффективности и сравнение стратегий.
Исторические свечи загружаются через публичный Binance Spot Market Data API;
для работы без сети доступен отдельный источник синтетических данных.
REST API объединяет загрузку свечей, стратегии, бэктестинг и сравнение с Buy & Hold.
Внешних Go-зависимостей нет. Архитектура — модульный монолит; расчёты
отделены от HTTP и не зависят от биржи, БД и frontend.

Этап 7.3 добавляет интерактивные графики Lightweight Charts к React frontend:
свечи, рассчитанные Go линии SMA, маркеры исполнений и equity curve.
Справочники, расчёты, метрики и история ордеров используют Go API.
Следующие шаги — публикация frontend на Cloudflare Pages и позднее PostgreSQL
через `pgx`.

```text

web/                        — React + TypeScript frontend (этап 7.3)
```

## Frontend — этапы 7.2–7.3

React + TypeScript + Vite, CSS с переменными, Lucide React. Frontend находится
в `web/` и собирается в статические файлы. Требуются Node.js 24.11.0+ и npm.

На Windows все установки, кэши и временные файлы размещаются на D:.
Переменные ниже действуют только в текущем PowerShell-сеансе:

```powershell

New-Item -ItemType Directory -Force D:\NpmCache, D:\FrontendTemp | Out-Null
$env:npm_config_cache = "D:\NpmCache"
$env:TEMP = "D:\FrontendTemp"
```

Если `.env.local` уже существует, отредактируйте его без перезаписи.
Для повторяемой установки зависимостей используйте `npm ci`.
Минимальный запуск после настройки окружения:

```bash
cd web
npm install
npm run dev
```

Откройте http://127.0.0.1:5173 (или http://localhost:5173).
В `web/.env.local` задаётся публичный адрес backend:

Шаблон `web/.env.example` хранится в Git; `.env.local` исключён.

### CORS на Render

Go-код уже поддерживает точный список origins через `CORS_ALLOWED_ORIGINS`.
В Render → Web Service → Environment вручную укажите:

```env
CORS_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

При использовании preview добавьте отдельно `http://localhost:4173`
и/или `http://127.0.0.1:4173`. В дальнейшем добавьте точный HTTPS origin
Cloudflare Pages. Origins задаются без пути и завершающего слеша.
localhost и 127.0.0.1 — разные origins; wildcard не используется.
Изменение окружения и перезапуск Render пользователь выполняет отдельно;
в этом этапе настройки сервера автоматически не меняются.

### Работа приложения

При открытии загружаются markets и strategies; доступные значения,
defaults и лимиты берутся из API. При сбое доступны Retry и отмена ожидания,
без фиктивных справочников. Форма проверяет UTC-даты с точностью до дня,
капитал, проценты, периоды SMA и общие лимиты истории с прогревом.
End date не включается. Для Buy & Hold параметры SMA не передаются.

Run Backtest отправляет один POST. Повторный submit блокируется, запрос
можно отменить. Клиент ждёт справочники до 120 секунд, бэктест до 90 секунд;
через 8 секунд напоминает о возможном холодном старте Render.
HTTP 504 от Go/Binance показывается отдельно от истечения клиентского
ожидания. Лимиты backend не менялись. Polling, keep-alive запросов
и автоматических повторов POST нет.

Ответ проверяется на соответствие структуре перед отображением.
В React state сохраняется весь результат, включая equity_curve, indicators,
trades и market. Метрики и Buy & Hold берутся из Go; frontend только
форматирует значения. Null-метрики отображаются как —. Разница доходности
показывается в процентных пунктах. Для Buy & Hold сравнение с собой скрыто.
Таблица ордеров прокручивается внутри панели. В начале нового запуска старый
результат очищается; редактирование формы не меняет контекст уже завершённого
расчёта. Отмена прекращает ожидание/соединение со стороны клиента;
завершение вычисления на сервере зависит от передачи отмены через сеть.

Графики используют реальные данные backend; они описаны ниже. Нет случайных
линий, синтетических результатов в production, сохранения результатов или live trading.

### Интерактивные графики — этап 7.3

Используется `lightweight-charts@5.2.1` (TradingView):
[официальная документация](https://tradingview.github.io/lightweight-charts/docs).
Применяются API v5: createChart, addSeries(CandlestickSeries/LineSeries),
createSeriesMarkers. Атрибуция TradingView сохранена на странице и графиках.

Market Chart (480 px на desktop) отображает исторические OHLC-свечи,
Fast SMA #D4D4D4 и Slow SMA #777777 из ответа Go. Для Buy & Hold линии SMA
отсутствуют. Свечи BUY/SELL зелёные/красные; остальной интерфейс остаётся
чёрно-белым. Есть zoom, pan, crosshair, значения OHLC/UTC-время над графиком
и Reset market view. При наведении на свечу исполнения показываются
BUY/SELL, время, цена, количество и комиссия.

В backtest response нет свечей: после успешного POST выполняется один
GET /api/v1/candles по фактическим symbol/interval/start/end результата,
а не по изменённой после запуска форме. Метрики и equity остаются доступны
при ошибке загрузки свечей. Есть Cancel candle loading и Retry candles.
Последний успешный набор кэшируется в памяти по рынку и периоду; повторный
расчёт или смена стратегии на том же диапазоне не вызывает второй GET.
Изменение полей формы само по себе запросы не отправляет. Новая загрузка
отменяет устаревшую. Polling и WebSocket не используются.

ISO UTC преобразуется в Unix seconds через Math.floor(Date.getTime()/1000).
Данные сортируются на копии. Точные дубли удаляются, конфликтующие OHLC,
объёмы или значения индикатора/equity вызывают ошибку вместо тихой подмены.
Проверяются полнота торгового диапазона, source, метки времени и SMA
candle_index. Финансовые показатели и SMA во frontend не рассчитываются.

Маркеры используют **неизменённое trade.time исполнения**. Go уже применил
правило сигнала после закрытия N и исполнения на Open N+1; повторный сдвиг
на frontend не выполняется. Время сделки должно совпадать со свечой.

Equity Chart (270 px) использует только equity_curve из Go. Светло-серая линия,
начальный капитал как reference line, final equity и hover readout в USDT.
Значения equity относятся к закрытию свечи, а timestamp по контракту Go
остаётся меткой открытия этой свечи; график явно сообщает об этой семантике.
В benchmark нет equity curve, поэтому Buy & Hold сравнивается численно:
доходность, final equity и excess return в процентных пунктах. Кривая benchmark
из предположений не строится.

Chart instances хранятся в useRef; обновление hover не пересоздаёт графики.
При обновлении данных вызываются setData, setMarkers и fitContent.
ResizeObserver меняет размеры при перестроении dashboard. Обработчики,
marker plugin, observer и chart instance удаляются при unmount.
Пустой результат не заменяется синтетическим графиком.

### Разделы рабочего пространства

Frontend разделён на три вкладки без React Router: Overview (основные и
вторичные метрики, equity curve, benchmark), Charts (600 px свечной график
на desktop, серверные SMA и исполнения), Trades (все ордера).
Вкладки используют общее состояние результата и кэш свечей в App.
Переключение не отправляет запросы, не сбрасывает форму и не меняет результат.
Поддерживаются клавиши Left/Right/Home/End в навигации. Графики размонтируются
с очисткой обработчиков и ResizeObserver; при возврате строятся из кэша.

Форма изначально открыта. После успешного расчёта Collapse settings скрывает
её, Edit settings возвращает без сброса введённых данных. Единая строка Completed backtest показывает фактические параметры последнего
завершённого расчёта. Если форма изменена, показывается предупреждение о
необходимости повторного запуска; старые показатели не переименовываются. Charts получает всю ширину, открытая форма располагается
над ним; на узких экранах блоки перестраиваются вертикально.

Переключатели SMA и Trades управляют только отображением слоёв графика.
Текст BUY/SELL у маркеров убран; стрелки и фактическое время исполнения
сохранены, подробности доступны при наведении. В Trades есть фильтр Side
и сортировка колонок Time/Price/Quantity/Notional/Fee. Сортируется копия
массива; исходный результат backend не изменяется. Настройки отображения
сохраняются в App при переключении вкладок и сбрасываются только после
нового успешного расчёта. Данные расчёта и кэш свечей не меняются.

Доработка информационной архитектуры выполнена с использованием unslop
Дамира Соколовского (@heydamir, CC BY 4.0): спокойная чёрная палитра,
единый ритм отступов, основные и вторичные показатели разного веса,
минимум пояснений и декора.

Пояснения к метрикам, комиссиям, проскальзыванию и периодам SMA раскрываются
кнопками помощи с клавиатуры и мышью. OHLC в панели графика сокращены до
O/H/L/C с полными названиями в title. Подробные параметры и комиссии остаются
в Overview; Charts и Trades не повторяют большую карточку контекста.

## Локальный запуск

Требуется Go 1.27.3 или новее (стабильный выпуск). База данных, ключи API
и дополнительные сервисы для этого этапа не нужны.

Из корня репозитория:

```sh
go run ./cmd/api
```

По умолчанию сервер слушает `:8080` на всех сетевых интерфейсах.
Переменная окружения `PORT` задаёт порт от 1 до 65535. Если она отсутствует
или пуста, используется `8080`; некорректное значение останавливает запуск.

Пример в PowerShell:

```powershell
$env:PORT = "9000"
go run ./cmd/api
```

Пример в Linux/macOS:

```sh
PORT=9000 go run ./cmd/api
```

`.env` автоматически не загружается; настройки передаются через окружение.
Необязательная `CORS_ALLOWED_ORIGINS` — список frontend origins через запятую,
например `http://localhost:5173,https://frontend.example`. По умолчанию список
пуст: запросы браузера с `Origin` не разрешены. Origin задаётся без пути,
завершающего `/`, wildcard и учётных данных.

```powershell
$env:CORS_ALLOWED_ORIGINS = "http://localhost:5173"
go run ./cmd/api
```

Для остановки нажмите Ctrl+C. Сервер обрабатывает SIGINT/SIGTERM и даёт
активным запросам до 10 секунд на завершение, затем закрывает соединения.
Таймаут чтения заголовков — 5 секунд, чтения — 10 секунд, записи — 40 секунд,
ожидания следующего запроса — 60 секунд.

## REST API v1

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| GET | `/api/v1/markets` | Пары, таймфреймы и ограничения истории |
| GET | `/api/v1/strategies` | Стратегии, параметры, значения по умолчанию и ограничения |
| GET | `/api/v1/candles` | Реальные закрытые OHLCV-свечи |
| POST | `/api/v1/backtests` | Стратегия, бэктестинг, показатели и Buy & Hold |

```sh
curl http://localhost:8080/api/v1/markets
curl http://localhost:8080/api/v1/strategies
curl "http://localhost:8080/api/v1/candles?symbol=BTCUSDT&interval=1h&start=2024-01-01T00:00:00Z&end=2024-01-01T03:00:00Z"
curl -X POST http://localhost:8080/api/v1/backtests -H "Content-Type: application/json" --data-binary "@docs/examples/btcusdt-sma-request.json"
```

В Windows PowerShell используйте `curl.exe`. Готовый запрос
[BTCUSDT SMA](docs/examples/btcusdt-sma-request.json):

```json
{
  "symbol": "BTCUSDT",
  "interval": "1h",
  "start": "2024-01-01T00:00:00Z",
  "end": "2024-01-08T00:00:00Z",
  "initial_capital": 10000,
  "fee_percent": 0.1,
  "slippage_percent": 0,
  "strategy": {
    "type": "sma_crossover",
    "fast_period": 10,
    "slow_period": 30
  }
}
```

Для Buy & Hold используйте `"strategy": {"type": "buy_and_hold"}`.
`symbol`, `interval`, `start`, `end` и `strategy.type` обязательны.
Остальные поля имеют значения по умолчанию из примера. Явная комиссия 0
разрешена и не заменяется значением 0,1%. Null вместо входного параметра,
неизвестные JSON-поля, несколько JSON-объектов, лишние/повторные query-параметры
для свечей и SMA-параметры у Buy & Hold отклоняются. Для POST нужен
`Content-Type: application/json`. Время API принимает только RFC3339 с нулевым
UTC-смещением и точными границами свечей; в ответах используется `Z`.

Ответ `/candles` содержит `market` с фактическим диапазоном и источником,
а также массив `candles`: `open_time`, `open`, `high`, `low`, `close`, `volume`.
Backtest возвращает:

- `market`, `strategy`, `configuration` — фактический торговый период,
  источник и применённые параметры.
- `metrics` — `total_return`, `max_drawdown`, `completed_trades`, `win_rate`,
  `profit_factor`; доходность и просадка выражены в процентах.
- `portfolio` — `final_equity`, `cash`, `asset_quantity`, `total_fees`.
- `benchmark` — стратегия Buy & Hold, её `metrics`, `portfolio` и
  `excess_return` (доходность выбранной стратегии минус Buy & Hold, в п.п.).
- `trades` — исполненные операции с типом `buy`/`sell`, временем, ценой,
  количеством, стоимостью без комиссии, комиссией и остатками после операции.
- `equity_curve` — стоимость портфеля на закрытии каждой торговой свечи;
  время остаётся меткой `OpenTime` свечи согласно контракту движка.
- `indicators.fast_sma` и `indicators.slow_sma` — точки с индексом свечи
  торгового периода, временем и значением; для Buy & Hold массивы пустые.

Имена полей — snake_case. Неопределённые метрики — JSON `null`, пустые
журналы/серии — `[]`. ID бэктеста нет: результаты не сохраняются.

Полный [реальный JSON-ответ](docs/examples/btcusdt-sma-response.json) получен
через локальный REST API на исторических данных Binance за указанный период.
В нём 168 точек equity, 9 операций и 4 завершённые позиции. Например, раздел
`metrics` этого ответа:

```json
{
  "total_return": 3.2907927505975376,
  "max_drawdown": 3.9456580719694156,
  "completed_trades": 4,
  "win_rate": 25,
  "profit_factor": 2.6026832082178566
}
```

Конечная стоимость — 10329,079275 USDT, доходность Buy & Hold — 3,319358%,
разница — −0,028565 п.п. Это пример ответа и правил расчёта; параметры
не оптимизировались. При проверке другие обращения к Binance завершались
таймаутом: API возвращал 504, не подменяя историю синтетическими данными.

### Прогрев SMA

Для пользовательского периода `[start, end)` сервер загружает дополнительно
`slow_period` свечей до `start`. Это даёт две последовательные пары средних
уже при закрытии первой торговой свечи. Например, для SMA 10/30 на недельном
примере запрашиваются 198 свечей с 2023-12-30 18:00Z: 30 для прогрева и
168 для торговли.

Адаптер анализирует объединённую историю, отбрасывает сигналы до `start`
и переводит индексы остальных в координаты торгового периода. Затем
`backtest.RunContext` получает только торговые свечи. Капитал, equity,
журнал сделок и метрики не включают прогрев; графики SMA тоже обрезаны по
торговому периоду. Даже сигнал последней свечи прогрева не переносится
на первый торговый Open. Первый допустимый сигнал возникает после закрытия
первой торговой свечи и исполняется на следующем Open.

Buy & Hold использует тот же торговый период, начальный капитал, комиссию
и проскальзывание, без прогрева. Нужны как минимум две закрытые торговые
свечи. Лимиты 3000 свечей и 90/365 дней проверяются **вместе с прогревом**;
максимальная slow SMA — 2998, но конкретный диапазон может требовать меньшего
периода. Границы не сдвигаются молча для обхода лимитов. Недостаток данных
прогрева — ошибка источника, а не разрешение торговать без готовых средних.

### Ошибки и ограничения ресурсов

Все ошибки API имеют единый формат, например:

```json
{"error":{"code":"invalid_parameters","message":"start must be an RFC3339 UTC timestamp"}}
```

| HTTP | Ситуация |
| --- | --- |
| 400 | Некорректные параметры, схема или числовой диапазон |
| 403 | Запрос браузера с неразрешённым Origin |
| 404 | Неизвестный endpoint |
| 405 | Неподдерживаемый метод, заголовок `Allow` указывает допустимый |
| 408 | Контекст запроса отменён |
| 413 | JSON-тело больше 16 KiB |
| 429 | Заняты слоты тяжёлых запросов либо ограничение Binance |
| 502 | Некорректная/неполная история или неожиданный ответ источника |
| 503 | Источник недоступен, Binance 418/403/451 или ошибка сервера |
| 504 | Таймаут загрузки/расчёта либо upstream HTTP 504 |
| 500 | Непредвиденная внутренняя ошибка или невозможность сформировать ответ |

В ответах не раскрываются исходные ошибки сети, URL конфигурации и детали
сервера. Для 429/418 Binance переносится `Retry-After`, округлённый вверх
до секунд. Локальный 429 рекомендует повтор через секунду. Автоматических
повторов, очереди и постоянных фоновых процессов нет.

`/candles` и `/backtests` делят лимит **2 одновременных тяжёлых запросов**
на процесс. Лишние запросы сразу получают 429. Каждый принятый тяжёлый запрос
имеет общий таймаут **25 секунд**, а клиент Binance — 10 секунд на HTTP-запрос.
Контекст передаётся в загрузку, генерацию SMA, движок и метрики; циклы расчёта
проверяют отмену. Тело запроса ограничено 16 KiB, JSON-ответ — 2 MiB, число
свечей с прогревом — 3000 и дополнительно дневными лимитами провайдера.
Ответ бэктеста не дублирует OHLCV: для свечного графика есть `/candles`.

Разрешённому Origin возвращается его точное значение, без `*` и cookies.
Поддерживается OPTIONS preflight с методом endpoint и `Content-Type`;
`Retry-After` доступен браузеру. Неразрешённый Origin получает 403. CORS не
заменяет авторизацию или защиту от ботов: клиенты без Origin могут обращаться
к публичному API. Лимит действует в одном процессе, не распределяется между
репликами и сбрасывается после перезапуска. Персонального rate limiting нет.

HTTP-тесты используют FixtureProvider и локальные заглушки: реальный Binance
не требуется. Проверяются прогрев, время исполнения, метрики, лимиты,
ошибки upstream, CORS и отмена. Старые вызовы `backtest.Run`, `Analyze` и
`CalculateMetrics` сохранены; их варианты с контекстом используются HTTP API.

Перед контейнеризацией и бесплатным деплоем задайте точные frontend origins,
проверьте доступ к Binance из выбранного окружения, поведение таймаутов и
завершения процесса, а также лимиты под доступную память. Для публичного
интернета стоит ограничить частоту запросов на внешнем прокси. Докеризация,
деплой и подключение frontend на этом этапе не выполняются.

## Ядро бэктестинга

Пакет `github.com/ilyagrechinskii/TradeLab/internal/backtest` доступен коду
внутри этого репозитория согласно правилам Go для `internal`. Это отдельный
расчётный пакет в существующем Go-модуле, без собственного HTTP API.

Основные функции:

```go
func DefaultConfig() Config
func (cfg Config) Validate() error
func ValidateCandles(candles []Candle) error
func Run(candles []Candle, signals []Signal, cfg Config) (BacktestResult, error)
func CalculateMetrics(result BacktestResult) (Metrics, error)
```

Модели: `Candle`, `Signal`, `SignalType` (`Hold`, `Buy`, `Sell`), `Config`,
`Portfolio`, `Trade`, `EquityPoint`, `BacktestResult`. Результат содержит
капитал, итоговую equity, доходность в процентах, сумму комиссий, исполненные
операции, equity curve и конечные остатки денег и актива.

Пример вызова (внутри функции; нужны импорты `fmt`, `time` и пакета `backtest`):

```go
start := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
candles := []backtest.Candle{
    {OpenTime: start, Open: 100, High: 100, Low: 100, Close: 100},
    {OpenTime: start.Add(time.Hour), Open: 100, High: 110, Low: 100, Close: 110},
    {OpenTime: start.Add(2*time.Hour), Open: 120, High: 120, Low: 120, Close: 120},
}
signals := []backtest.Signal{
    {CandleIndex: 0, Type: backtest.Buy},
    {CandleIndex: 1, Type: backtest.Sell},
}
cfg := backtest.DefaultConfig()
cfg.InitialCapital = 1010
cfg.FeePercent = 1 // 1%, а не доля 0.01.
result, err := backtest.Run(candles, signals, cfg)
if err != nil {
    panic(err)
}
fmt.Printf("Equity: %.2f, fees: %.2f, return: %.2f%%\n",
    result.FinalEquity, result.TotalFees, result.TotalReturn)
// Equity: 1188.00, fees: 22.00, return: 17.62%
```

Этот пример также проверяется командой `go test ./...` как `ExampleRun`.

Правила расчёта и ограничения:

- По умолчанию: капитал 10 000, комиссия 0,1%, проскальзывание 0%.
  Все суммы выражены в одной валюте котировки, например USDT.
  `Run` использует переданный конфиг без подстановки значений: нулевая комиссия
  допустима, нулевой начальный капитал — ошибка. Проценты конечные, от 0
  включительно до 100 исключительно.
- Сигнал после закрытия свечи N исполняется по `Open` свечи N+1.
  Проскальзывание увеличивает цену покупки и уменьшает цену продажи.
  Сигнал последней свечи не исполняется.
- Разрешены только одна Spot-позиция, покупка на весь денежный баланс
  и продажа всего актива. Повторный Buy и Sell без позиции игнорируются.
  Отсутствующий сигнал равнозначен Hold. Сигналы могут поступать в любом порядке;
  индексы должны быть допустимыми и уникальными, включая Hold.
- Комиссия списывается в валюте котировки. Количество при покупке рассчитывается
  как `Cash / (1 + FeePercent/100) / ExecutionPrice`. При погрешности округления
  оно уменьшается до доступного количества; возможен малый денежный остаток.
  `Trade.Notional` — стоимость актива без комиссии; денежный расход на Buy
  равен `Notional + Fee`, поступление от Sell — `Notional - Fee`.
- После каждой свечи: `Equity = Cash + AssetQuantity * Close`. Открытая позиция
  в конце остаётся открытой и оценивается без гипотетической комиссии за выход.
  `TotalReturn = (FinalEquity / InitialCapital - 1) * 100`.
- Время исполнения — открытие следующей свечи в UTC. В equity curve время —
  `OpenTime` оцениваемой свечи в UTC, а стоимость рассчитана на её закрытии.
  Это метка свечи: точное время закрытия невозможно вывести без её интервала.
- Требуется хотя бы одна корректная свеча. Временные метки строго возрастают,
  пропуски интервалов допускаются; исполнение происходит на следующей
  предоставленной свече. Входные срезы не изменяются. Некорректные данные,
  неизвестные/дублирующиеся сигналы и непредставимые результаты `float64`
  возвращают ошибку без частичного результата.
- Используется `float64`, без правил биржевого округления, lot size,
  минимальной стоимости ордера, ликвидности и частичных исполнений.
  Объём валидируется, но не ограничивает исполнение. Сигналы предоставляются
  вызывающим кодом: их генератор должен самостоятельно избегать будущих данных.
- Журнал хранит исполненные операции, а не пары «вход — выход».
  Метрики вычисляются отдельно через `CalculateMetrics`.

## Стратегии и показатели

Пакет `internal/strategy` зависит от моделей и публичного API `backtest`.
Обратной зависимости нет. Контракт стратегии содержит один метод:

```go
type Strategy interface {
    Generate(candles []backtest.Candle) ([]backtest.Signal, error)
}
```

Стратегии только анализируют свечи и создают сигналы. Исполнение, комиссии,
проскальзывание и состояние портфеля остаются в `backtest.Run`.

Публичный API пакета `strategy`:

```go
func DefaultSMACrossover() SMACrossover
func (s SMACrossover) Validate() error
func (s SMACrossover) Generate(candles []backtest.Candle) ([]backtest.Signal, error)
func (s SMACrossover) Analyze(candles []backtest.Candle) (CrossoverResult, error)
func (BuyAndHold) Generate(candles []backtest.Candle) ([]backtest.Signal, error)
func SMA(candles []backtest.Candle, period int) ([]SMAPoint, error)
func Run(candles []backtest.Candle, selected Strategy, cfg backtest.Config) (Report, error)
func CompareWithBuyAndHold(candles []backtest.Candle, selected Strategy, cfg backtest.Config) (Comparison, error)
```

`SMACrossover` задаёт `FastPeriod` и `SlowPeriod`, по умолчанию 10 и 30.
Нужно `0 < FastPeriod < SlowPeriod` и не менее `SlowPeriod + 1` свечей:
пересечение требует двух полных окон медленной SMA. Нулевые параметры
не заменяются значениями по умолчанию — используйте `DefaultSMACrossover()`.

Обе SMA считаются по `Close` скользящей суммой с компенсацией погрешности,
за O(n), без пересчёта каждого окна. `Analyze` возвращает сигналы и обе серии
для графика. Точки `SMAPoint` содержат индекс свечи, её `OpenTime` в UTC и
среднее; до завершения окна точек нет. Отдельная `SMA` требует хотя бы
`period` свечей. Переполнение суммы или неположительное вычисленное среднее
возвращает ошибку.

BUY возникает при переходе быстрой SMA снизу вверх относительно медленной,
SELL — сверху вниз. Первое доступное положение средних само по себе сигналом
не является. При равенстве сигнал не создаётся; сохраняется последняя строго
неравная сторона. Поэтому касание с возвратом на ту же сторону не даёт
повторный BUY/SELL, а переход через равенство на противоположную — даёт.
Если первая пара средних равна, выход из равенства создаёт первый сигнал.
Сигналы последней свечи сохраняются, но движок их не исполняет.

Buy & Hold требует минимум две свечи и генерирует ровно один BUY на индексе 0.
Покупка исполняется на `Open` свечи 1. Принудительной продажи в конце нет.

Прямой запуск SMA Crossover через прежний API движка (для подготовленных
свечей `candles`, с импортами `backtest` и `strategy` из `internal`):

```go
selected := strategy.DefaultSMACrossover()
cfg := backtest.DefaultConfig()
signals, err := selected.Generate(candles)
if err != nil {
    return err
}
result, err := backtest.Run(candles, signals, cfg)
if err != nil {
    return err
}
metrics, err := backtest.CalculateMetrics(result)
if err != nil {
    return err
}
fmt.Printf("Доходность: %.2f%%, максимальная просадка: %.2f%%\n",
    result.TotalReturn, metrics.MaxDrawdown)
```

`strategy.Run(candles, selected, cfg)` объединяет эти шаги и возвращает `Report`
с полями `Result` и `Metrics`. Для сравнения с контрольной стратегией:

```go
comparison, err := strategy.CompareWithBuyAndHold(candles, selected, cfg)
if err != nil {
    return err
}
fmt.Printf("SMA: %.2f%%, Buy & Hold: %.2f%%, разница: %.2f п.п.\n",
    comparison.Strategy.Result.TotalReturn,
    comparison.BuyAndHold.Result.TotalReturn,
    comparison.ExcessReturn)
```

Оба запуска используют весь переданный интервал и один `cfg`. Период прогрева
SMA включён в интервал сравнения: SMA в это время держит деньги, Buy & Hold
уже может владеть активом. `ExcessReturn` — разность доходностей в процентных
пунктах. Доходность Buy & Hold берётся из того же движка, а не из отношения
первого и последнего `Close`.

Полные проверяемые примеры с фиксированными свечами:
`internal/strategy/example_test.go`. На этих демонстрационных данных SMA даёт
100%, Buy & Hold −50%, разница — 150 п.п.; это проверка правил исполнения,
а не оценка реальной прибыльности стратегии.

`backtest.CalculateMetrics` принимает результат движка и возвращает:

- `TotalReturn` — доходность, уже рассчитанную движком.
- `MaxDrawdown` — максимальное процентное падение от предшествующего пика;
  начальный капитал включается как первый пик. Показатель неотрицательный.
- `CompletedTrades` — число завершённых пар Buy/Sell, а не число ордеров.
- `WinRate` (`*float64`) — долю прибыльных закрытых позиций в процентах.
- `ProfitFactor` (`*float64`) — сумму положительных PnL, делённую на модуль
  суммы отрицательных PnL.

PnL закрытой позиции: `(Sell.Notional - Sell.Fee) - (Buy.Notional + Buy.Fee)`.
Проскальзывание уже входит в исполненные цены и `Notional`. Незакрытая
позиция участвует в общей доходности и просадке через equity curve, но
не участвует в Win Rate и Profit Factor. Безубыточная позиция считается
завершённой, но не прибыльной и не убыточной.

| Ситуация | Win Rate | Profit Factor |
| --- | --- | --- |
| Нет завершённых позиций | `nil` | `nil` |
| Есть прибыль, нет убытков | Рассчитан | `nil` |
| Только безубыточные позиции | 0% | `nil` |
| Все позиции убыточные | 0% | 0 |
| Есть прибыль и убытки | Рассчитан | Рассчитан |

`nil` означает неопределённый показатель и сериализуется как JSON `null`.
NaN/Infinity не возвращаются. Метрики рассчитаны на формат текущего движка:
одна позиция и полное закрытие. Некорректная последовательность операций,
частичные продажи, невалидные числа и переполнение возвращают ошибку.
Сравнение SMA использует обычную точность `float64`, без настраиваемого
порога пересечения. Sharpe Ratio, Sortino Ratio и оптимизация параметров
не реализованы.

## Исторические свечи Binance

`internal/marketdata` использует существующий `backtest.Candle`. Источник
данных заменяется через небольшой интерфейс:

```go
type Provider interface {
    GetCandles(ctx context.Context, symbol, interval string, start, end time.Time) ([]backtest.Candle, error)
}

func NewBinance(options BinanceOptions) (*Binance, error)
func NewFixtureProvider(symbol, interval string, candles []backtest.Candle) (*FixtureProvider, error)
```

Оба провайдера реализуют `Provider`. `BinanceOptions` содержит необязательные
`BaseURL`, `HTTPClient` и часы `Now` для тестов. Пустые опции используют
`https://data-api.binance.vision`, общий клиент с таймаутом 10 секунд на запрос
и `time.Now`. Переданный HTTP-клиент копируется; его положительный таймаут
сохраняется, редиректы отключаются. Ключ API не нужен, торговые и приватные
endpoint не используются.

Формат и параметры сверены с официальной документацией:
[Klines](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md#klinecandlestick-data),
[Market Data Only](https://github.com/binance/binance-spot-api-docs/blob/master/faqs/market_data_only.md).
Запросы отправляются только на `GET /api/v3/klines`, с `timeZone=0`,
`startTime`/`endTime` в Unix **миллисекундах**. Для ответов используется
документированный формат миллисекунд по умолчанию; заголовок включения
микросекунд намеренно не устанавливается. Проверяются и Open time, и Close time.

Пример использования внутри репозитория (импорты `context`, `fmt`, `time` и `marketdata`):

```go
provider, err := marketdata.NewBinance(marketdata.BinanceOptions{})
if err != nil {
    return err
}
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
start := time.Date(2024, 1, 1, 0, 0, 0, 0, time.UTC)
candles, err := provider.GetCandles(ctx, "BTCUSDT", "1h", start, start.Add(6*time.Hour))
if err != nil {
    return err
}
fmt.Printf("Получено %d свечей\n", len(candles))
// candles также можно передать в strategy.Run или backtest.Run.
```

Правила диапазона и проверки:

- Поддерживаются 12 пар из общего справочника marketdata.Markets() и интервалы 1h, 4h, 1d (полный список — в разделе RU/EN).
- Интервал — `[start, end)`. Времена переводятся в UTC, но не округляются:
  неверная граница возвращает ошибку. Для `4h` допустимы 00:00, 04:00,
  08:00 и т.д. UTC, для `1d` — 00:00 UTC. Даты должны быть в 1970–9999 годах.
- Запрошенный диапазон ограничен 3000 свечами и дополнительно 90 днями для
  `1h`, 365 днями для `4h` и `1d`. Применяются оба ограничения; фактический
  максимум при этих таймфреймах может быть меньше 3000.
- Конец диапазона обрезается до открытия текущей свечи, если запрошено
  настоящее/будущее. Граница фиксируется в начале загрузки. Текущая свеча
  исключается; диапазон без закрытых свечей возвращает ошибку. Проверяется
  завершённость по Close time и полной длительности свечи, с учётом часов хоста.
- Пагинация запрашивает до 1000 свечей за страницу, не более 10 HTTP-запросов
  на загрузку. Курсор — открытие следующей свечи после последней полученной;
  включительный Binance `endTime` равен нашему `end - 1ms`.
- Ответ ограничен 1 MiB на страницу. OHLCV проверяется через
  `backtest.ValidateCandles`; дополнительно проверяются границы, порядок,
  непрерывность и полное покрытие закрытой части диапазона. Разрыв, повтор,
  пустая/недостаточная история или неверный формат дают ошибку без частичных
  данных. Свечи не сортируются и не дополняются выдуманными значениями.
- HTTP 429, 418, 403/451 и 5xx возвращают `*marketdata.HTTPError`, доступный
  через `errors.As`. Поля: `StatusCode` и `RetryAfter` (`time.Duration`).
  Для 429/418 разбираются секунды и HTTP-дата из `Retry-After`; отсутствующий
  или некорректный заголовок даёт нулевую задержку. Автоматических повторов нет;
  вызывающий код должен соблюдать полученную задержку перед новой попыткой.
- Сетевые ошибки, таймауты и отмена контекста сохраняют исходную причину
  через обёртки, например для `errors.Is(err, context.Canceled)`.

Ручная проверка реального API без запуска HTTP-сервера:

```sh
go run ./cmd/marketcheck
```

Команда запрашивает BTCUSDT `1h` за `[2024-01-01T00:00Z, 2024-01-01T06:00Z)`,
выводит количество, первую/последнюю метки и три примера OHLCV. Ожидается
6 свечей с метками от 00:00Z до 05:00Z. Общий таймаут команды — 30 секунд.
При недоступности API команда завершается с ошибкой и не подменяет котировки.

Работа без сети:

```sh
go run ./cmd/marketcheck -fixture
```

Этот режим использует `FixtureProvider` с шестью заранее заданными
**синтетическими демонстрационными** свечами и явно сообщает об этом в выводе.
`NewFixtureProvider` принимает собственный набор данных для одной пары и
таймфрейма, проверяет его и копирует; результаты тоже возвращаются копиями.
Для запроса применяются те же ограничения диапазона и полноты истории.

Обычный `go test ./...` работает без интернета: тесты используют
`httptest.Server` и подготовленные ответы. Реальный интеграционный тест
по умолчанию пропускается. Явный запуск в PowerShell:

## RU/EN и расширенные рынки

Интерфейс поддерживает русский и английский через react-i18next.
Единая конфигурация — `web/src/i18n/config.ts`, словари — `ru.json`
и `en.json`. При первом открытии выбирается RU для языка браузера ru,
иначе EN. Выбор кнопками RU/EN сохраняется в localStorage под ключом
`tradelab.language`. При недоступном хранилище приложение продолжает работать.
Перевод не перезагружает страницу, не пересоздаёт графики и не меняет
параметры/результат/сортировку/слои. Даты и числа форматируются через Intl.
Тикеры, интервалы, JSON-поля и идентификаторы стратегий не переводятся.

Источник разрешённых пар — Go `marketdata.Markets()`. В `GET /api/v1/markets`
сохранено поле `symbols` и добавлено необязательное для старых клиентов поле
`instruments: [{symbol, name}]`. Frontend строит поиск только по этому ответу.
Поиск учитывает тикер и имя, Enter/ArrowDown переводят фокус на список,
Escape очищает поиск. Изменение выбора не запускает бэктест автоматически.
Старый Render без instruments остаётся совместим: отображаются его реальные
символы без выдуманных названий и без добавления новых пар на стороне клиента.

Поддерживаемые обновлённым backend инструменты:
BTCUSDT (Bitcoin), ETHUSDT (Ethereum), SOLUSDT (Solana), BNBUSDT (BNB),
XRPUSDT (XRP), ADAUSDT (Cardano), DOGEUSDT (Dogecoin), LINKUSDT (Chainlink),
AVAXUSDT (Avalanche), LTCUSDT (Litecoin), TRXUSDT (TRON), DOTUSDT (Polkadot).

Проверка 02.11.2026: Binance Spot exchangeInfo подтвердил для всех 12 пар
status=TRADING и isSpotTradingAllowed=true. Для каждой пары через существующий
data-api.binance.vision/api/v3/klines получены две непрерывные свечи 1h за
[2024-01-01T00:00Z, 2024-01-01T02:00Z). Это проверка доступности источника
и выбранного периода; она не гарантирует наличие истории до листинга монеты.
Пустая, неполная история и ограничения диапазона обрабатываются как прежде.
Обычные тесты используют mock Binance/FixtureProvider и не требуют сети.

### Обновление Render после изменения backend

Новые пары доступны **только в обновлённом локальном backend**, пока изменения
не отправлены и не развёрнуты на Render. Наличие нового frontend этого не меняет.

После проверки и отдельного разрешения пользователя:
1. Закоммитить и отправить изменения backend на GitHub.
2. В Render открыть существующий Web Service и выбрать Manual Deploy →
   Deploy latest commit (Auto-Deploy в проекте выключен).
3. Дождаться успешного health check /healthz.
4. Проверить /api/v1/markets: 12 symbols и соответствующие instruments.
5. Выполнить короткую проверку /candles и /backtests с новой парой.
6. Сохранить настроенный CORS_ALLOWED_ORIGINS; проверить frontend с реальным API.

Этот этап не выполняет commit, push или deploy и не меняет конфигурацию Render.
Торговый движок, SMA, комиссии, исполнение N+1, валидация OHLCV, лимиты свечей
и непрерывность истории не изменялись.
